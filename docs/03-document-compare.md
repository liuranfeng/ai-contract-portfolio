# 03 · 独立文档比对（签前核对）

**形态**：套件源码（7 个 Skill）+ 交互演示
**状态**：本地工程样本验证通过；可独立调用，也可由业务系统编排调用

## 问题定义

签约前最常见的风险不是「合同写得不好」，而是**待签稿与审批通过的版本不一致**——改了一个百分比、放宽了一个期限、换了一段措辞，流程上却看不出来。签前核对需要的是「可复核的差异」，而不是一句「基本一致」。

## 逐 layout 比对

复用文档解析能力，按**阅读顺序逐 layout** 对齐两份文档，而不是按字符流做 diff。这样得到的差异天然带段落语义与原文位置，可以直接定位回文档页面。

## 两种校验模式的适用边界

| 模式 | 判定依据 | 适用场景 |
| --- | --- | --- |
| 字符一致性 | 逐字符比对 | 金额、比例、期限、引用编号等必须逐字一致的内容 |
| 语义一致性 | 业务等义判定 | 表述改写但义务相同（如「验收合格后 30 日内付款」与「以验收通过为付款前提，付款期限 30 日」） |

两种模式并非二选一：对同一份文档可以分区域使用不同模式，兼顾「锁定关键措辞」与「容忍无害改写」。

## 交付形态

- **三屏联动**：原件 / 比对件 / 差异清单，差异条目与两侧原文联动高亮
- **Word 原生修订输出**：以原件为基准生成修订稿，可在 Word 中逐条接受或拒绝，不是图片或批注式标注
- **报告**：差异清单 + 统计 + 逐条定位

## 验收语义（本地工程样本）

| 校验项 | 结果 |
| --- | --- |
| 原件未被改写 | 通过 |
| 接受全部修订后 = 目标稿 | 通过 |
| 拒绝全部修订后 = 原件 | 通过 |
| 修订为 Word 原生格式 | 通过 |

> 样本为合成的工程样本（非客户数据），上述结论只支撑该样本的验收语义，不代表通用效果。

## 套件结构（suites/document-compare）

解析（contract-parsing）→ 输入适配（document-layout-input）→ 逐 layout 比对（document-compare）→ 语义校验（document-semantic）→ 三屏 HTML（document-diff-html）→ Word 修订（document-word-edit）→ 报告（document-diff-report）。
