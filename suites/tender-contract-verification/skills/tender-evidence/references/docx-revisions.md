# DOCX 修订、解析版本与“最终合同”

DOCX 存在跟踪修订时，解析器抽取的混合文本不能直接当作最终约定。典型错误是同一句里同时出现被删除的旧附件名和插入的新附件名，或者把插入的负责人姓名直接报为签署合同已落实。

## 取得三个彼此分开的证据视图

1. **原始修订包**：只读保存源 DOCX、哈希以及原始 XML；记录 `w:ins`、`w:del`、`w:moveFrom`、`w:moveTo` 等修订标记及所在段落/表格。格式修订、域、文本框、页眉页脚与表格结构修订同样可能影响解释。
2. **原版本视图**：按拒绝修订的语义展示变更前内容。不能仅删除所有带标记 XML 节点；删除文本通常存于 `w:delText`，移动和表格修订也要处理。
3. **接受修订视图**：按接受修订的语义展示变更后内容。使用能正确处理对应修订类型的文档引擎生成派生副本；简单 XML 筛选仅作有范围声明的辅助核查，不能声称等同 Word 最终版。

两个视图都不自动等于“最终确认/签署版本”。结合已提供签署 PDF、版本日期、确认记录和附件清单确定本次对照对象。若无法确定，则明确“按接受修订视图可见……，最终采用版本待确认”，结论为落实待确认或基准待澄清，不能直接判定落实/撤回。

## 血缘与定位

- 原 DOCX 和每个渲染/解析派生文件各有文件索引、哈希及版本标签，记录共同父文件；不得覆盖源 DOCX 或偷偷接受修订。
- `layoutId` 仅来自该版本的解析结果，不能把 accepted 视图的 ID 拿去指 original 视图。跨版本对应是一条关联关系，需双方真实引用和关联理由。
- XML 段落序号只是结构核查线索，不伪造为原生 layoutId；无法获得版面定位时明确标记定位待补，并保留原始 XML 路径和内容佐证。
- 解析器输出若混合删除和插入文本，保留输出并标为 `mixed_revision_text` 待确认。不能通过手工改写这块 text 假装 OCR 原文正确。必要时分别渲染、解析两个派生视图。

## 判断顺序

首先确定比较基准和文档版本；再提取具体承诺；然后查看正文、附件、纳入条款、优先顺序、排除或例外；最后判断是否低于预期。例如合同一般写“满足投标文件所有承诺”，该文字若只在插入修订中出现，就必须把纳入路径标为条件性证据；不能据此消除所有承诺缺口。

金额、人员姓名、期限、附件名或纳入条款受到修订影响时，报告同时展示两个视图的差异、各自定位和最终版本不明对结论的影响。没有受修订影响的技术附件可独立核验，但不能因此推断整份合同的修订已全部确认。

## 复核清单

- 原始/接受视图是否被分别保存并标名？混合抽取是否显式标记？
- 负责人、纳入条款、附件目录和技术附件是否采用同一个已确认版本？
- 若只能核对部分 XML 修订类型，是否记录未覆盖范围，而非宣称完整 Word 语义？
- HTML 和 PDF 是否持续显示版本条件，而不是在摘要中变成确定结论？
